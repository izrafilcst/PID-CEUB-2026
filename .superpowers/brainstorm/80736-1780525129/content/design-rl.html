Design: Observation · Action · Reward

Seção 2 de 4 — o contrato de aprendizado. Há 2 decisões abertas marcadas em amarelo.

Observation Space — 14 dims, normalizado [-1, 1] ou [0, 1]

# Variável Faixa Fonte (real)
0–78× sensor IR[0, 1]SensorArray normalizado
8–9rpm_L, rpm_R[-1, 1] (÷ MAX_RPM)VelocityEstimator
10–11Δrpm_L, Δrpm_R[-1, 1]derivada encoder (proxy de inércia)
12erro_posição[-1, 1]SensorArray.readPosition()
13edf_pwm atual[0, 1]último comando EDF

Action Space — 3 dims contínuos (tanh)

a[0] = Δpwm_L ∈ [-1, 1] → × RESIDUAL_CLIP × 1023
a[1] = Δpwm_R ∈ [-1, 1] → × RESIDUAL_CLIP × 1023
a[2] = pwm_EDF ∈ [-1, 1] → remapeado p/ [0, 1023] (absoluto)

# Composição final (idêntica sim e real):
pwm_L = clip(pid_base_L + Δpwm_L, -1023, 1023)
pwm_R = clip(pid_base_R + Δpwm_R, -1023, 1023)
set_edf(pwm_EDF)

Δpwm é residual sobre o PID (correção). EDF é absoluto (a NN controla 100% o ventilador, já que o PID não toca nele).

Reward — velocidade com precisão

r = + k_prog · Δdist_ao_longo_da_pista  # incentiva velocidade
   − k_track · |erro_posição|       # incentiva precisão
   − k_slip · slip_lateral         # incentiva downforce/controle
   − k_edf · edf_pwm            # custo de energia (DECISÃO ABERTA)
   − 100 se linha_perdida       # termina episódio
   + 50 se completou volta      # bônus de conclusão

⚠ 2 decisões abertas

1. RESIDUAL_CLIP — quanto a NN pode desviar do PID? Menor = mais seguro mas menos poder; maior = mais liberdade mas risco de ignorar o PID. (recomendo 0.3 = ±30%)

2. Custo de EDF (k_edf) — penalizar uso do ventilador? Sem custo → NN deixa EDF no máximo sempre. Com custo → NN aprende a usar EDF só quando precisa (curva). (recomendo custo pequeno, para comportamento interessante e poupar bateria)

Nota de fidelidade sim→real: o env precisa rodar um PID de referência em Python que espelhe o CascadeController C++ — porque o Δpwm só faz sentido relativo a um baseline conhecido. Esse PID-Python é parte do design e será validado contra o firmware.
